# Forge to Runtime Handoff Contract

## Purpose

This document defines the handoff contract that allows InferEdgeRuntime to reproducibly execute deployment artifacts generated by InferEdgeForge.

Forge owns artifact generation and provenance capture. Runtime owns artifact execution and profiling. The handoff contract keeps those responsibilities separate while making the artifact, metadata, and manifest usable in the end-to-end InferEdge validation pipeline.

## Handoff Flow

```text
ONNX model
-> InferEdgeForge build
-> deployment artifact
-> metadata.json
-> manifest.json
-> InferEdgeRuntime run
-> Lab-compatible result JSON
-> InferEdgeLab compare/report/deployment_decision
```

The expected flow is:

1. A user provides an ONNX model and a Forge preset.
2. Forge creates a deployment artifact such as `model.engine` or `model.rknn`.
3. Forge writes `metadata.json` for downstream handoff and inspection.
4. Forge writes `manifest.json` as a reproducibility and traceability snapshot.
5. Runtime uses the artifact path and runtime fields to execute or profile the artifact.
6. Runtime exports Lab-compatible result JSON.
7. Lab compares, reports, and owns the deployment decision.

## Artifact Ownership

- Forge owns build artifact generation.
- Runtime owns artifact execution/profiling.
- Lab owns analysis/report/deployment_decision.
- AIGuard optionally consumes provenance/failure evidence.

Forge should preserve enough information for Runtime, Lab, and AIGuard to trace a result back to the source model, preset, artifact, and target environment. Forge should not own Runtime backend behavior, Lab comparison policy, or Guard diagnosis.

## metadata.json Role

`metadata.json` is the handoff metadata for a produced build. It is optimized for inspection, CLI views, and downstream handoff commands.

It contains:

- build preset, backend, target, timestamp, and build id
- source model path, format, and SHA-256
- deployment artifact path, format, role, and SHA-256
- preset snapshot with build options and preset metadata
- Lab/Runtime compatibility mapping under `lab_compat.runtime`

`metadata.json` is the best source for user-facing inspection and handoff commands such as showing a Lab profile input or previewing compare-ready candidates.

## manifest.json Role

`manifest.json` is an immutable-ish build snapshot for reproducibility and traceability. It should remain stable enough for rebuild, artifact review, and Runtime input preparation.

It contains:

- `build_id` and build timestamp
- source model path, format, and SHA-256
- primary artifact path, format, role, SHA-256, model alias, and precision
- Runtime-oriented execution defaults under `runtime`
- preset snapshot used for the build
- tool version and Python version

The manifest does not guarantee bitwise-stable TensorRT or backend artifacts. It records the build recipe and provenance needed to reproduce and review the build as closely as the backend allows.

## Runtime-Required Fields

| Field | Source | Required | Purpose |
|---|---|---:|---|
| source model path or identifier | `source_model.path` | Required | Trace the artifact back to the original ONNX model. |
| source model SHA-256 | `source_model.sha256` | Recommended | Detect source model mismatch across rebuilds or validation runs. |
| backend | `build.backend`, `runtime.engine` | Required | Select or document the Runtime backend such as `onnxruntime`, `tensorrt`, or `rknn`. |
| target | `build.target`, `runtime.device` | Required | Identify the execution device or target family. |
| precision | `artifact.precision`, `runtime.precision`, `preset_snapshot.build_options.precision` | Required | Preserve the precision used for comparison and deployment decisions. |
| batch | `runtime.batch` or `lab_compat.runtime.requested_batch` | Recommended | Provide the intended batch size when known. |
| height | `runtime.height` or `lab_compat.runtime.requested_height` | Recommended | Provide the intended input height when known. |
| width | `runtime.width` or `lab_compat.runtime.requested_width` | Recommended | Provide the intended input width when known. |
| primary artifact path | `artifact.path`, `artifact.model_path`, `runtime.artifact_path`, `runtime.model_path` | Required | Tell Runtime which deployment artifact to execute. |
| primary artifact SHA-256 | `artifact.sha256` | Recommended | Detect artifact mismatch between build, execution, and diagnosis. |
| artifact type | `artifact.format` | Required | Identify artifact format such as `engine`, `rknn`, or `onnx`. |
| preset name | `build.preset_name`, `preset_snapshot.name` | Required | Preserve build intent and rebuild target. |
| preset snapshot | `preset_snapshot` | Recommended | Preserve effective build options and preset metadata. |
| build timestamp or build id | `build.timestamp`, `build.build_id` | Required | Tie execution evidence to a specific build record. |
| Lab/Runtime compatibility mapping | `lab_compat.runtime`, `runtime` | Recommended | Provide stable handoff aliases for Runtime and Lab. |

## Lab Compatibility Mapping

Forge metadata and manifest fields should flow into Runtime result JSON as follows:

| Forge field | Runtime result JSON field |
|---|---|
| `build.backend`, `runtime.engine` | `engine`, `engine_backend`, or `backend_key` |
| `build.target`, `runtime.device` | `device`, `device_name`, or target/device component of `backend_key` |
| `artifact.precision`, `runtime.precision`, `preset_snapshot.build_options.precision` | `precision` |
| `runtime.batch`, `lab_compat.runtime.requested_batch` | `batch` and `run_config.batch` |
| `runtime.height`, `lab_compat.runtime.requested_height` | `height` and `run_config.height` |
| `runtime.width`, `lab_compat.runtime.requested_width` | `width` and `run_config.width` |
| `artifact.path`, `artifact.model_path`, `runtime.artifact_path` | `model_path`, `extra.runtime_artifact_path`, or runtime provenance |
| `artifact.sha256` | runtime artifact provenance and AIGuard artifact mismatch evidence |
| `source_model.path` | `model_name`, `model.path`, or source model provenance |
| `source_model.sha256` | model provenance and AIGuard source mismatch evidence |
| `build.build_id`, `build.timestamp` | build provenance in reports or API bundles |

Runtime may still allow CLI overrides. When CLI values override manifest values, Runtime should record the resolved values in its result JSON so Lab can compare the actual execution configuration.

## Non-Goals

This document does not:

- make Forge own Runtime backend implementation
- make Forge own Lab compare logic
- make Forge own AIGuard diagnosis
- add a new build backend
- require TensorRT or RKNN conversion behavior changes in this step
